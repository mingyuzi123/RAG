2026-11-06。v3 自动英文查询已用于页面；条件父块/邻块策略已用于真实检索和回答，是手动选择的可选实验。同一开发/回归题集的完整回答为旧查询 5/10、v3 6/10、v3 加上下文规则 7/10。不能把这些结果当作新场景的默认表现。

## 5A 运行配置

`manifest.json` 的 `language` 描述资料语言，`retrieval` 配置 `strategy`、`top_k`、`context_k`、`context_policy` 和 `auto_rewrite`。`ui.json` 继续负责页面外观。CLI 参数或 API 请求字段优先于场景配置，缺省字段使用内置默认值。页面通过 `/api/config` 加载同一套默认值，请求由后端统一校验并处理改写。条件合并需要混合 RRF。显式 `context_k` 超过 Top K 会报错，只缩小 Top K 时则把默认上下文数一并缩小。

英文与混合场景默认 E5、候选 10、上下文 3、直接取前 K。英文场景允许按需自动改写，混合资料默认关闭。E5 直接使用原问题。关键词路线先用已填写的检索词，其次可使用纯 ASCII 原问题，最后按开关尝试 DeepSeek。CLI 用 `--auto-rewrite` 或 `--no-auto-rewrite` 覆盖开关，API 对应布尔字段 `auto_rewrite`。历史 CLI 的默认 BM25 改为按场景读取，本地免费关键词流程显式传 `--strategy bm25`。

2026-11-09 实测通过。Pydantic 使用同一条手填英文词和条件合并策略，API 与 CLI 的 3 个证据块 ID 顺序一致。本地混合文档使用 E5，显式 Top K 为 2 且省略上下文 K，两入口均选择同样的 2 个证据块。非法上下文数量、非布尔改写开关和混合资料缺少英文词的混合检索均返回明确的 400 错误。28 项单元测试通过。改写分支用模拟响应验证，真实检索对照使用本地索引。

复习时在页面把候选数与上下文数都设成 2，再用 CLI 只传 `--top-k 2`，对照同一问题的证据块 ID。这个改动属于运行参数。更换文档属于资料和索引变更，修改 RRF 公式属于算法变更。[共用解析代码](../raglab/runtime.py)

## 已触及但需要明确理解的问题

1. **各入口需要同一套默认值和覆盖规则。**5A 把参数和关键词解析集中到 `raglab/runtime.py`，可通过响应中的 `retrieval` 和证据块 ID 核对。
2. **语料语言决定处理方式。**英文查询适配英文文档；当前 BM25 过滤中文，中文/混合资料优先使用跨语言 E5。中文 BM25 需要分词/索引改造，不能靠把问题翻译成英文解决中文原文匹配。
3. **优化组合会相互影响。**查询词同时影响 BM25 候选和邻块规则，分别有效仍需组合评测；P01 没改善就是边界。
4. **“能回答”不等于“应回答”。**新验收集必须有资料中无答案的问题。引用编号存在也不等于结论得到支持；P04 出现过格式不被解析器识别，而 P01 出现过断言证据不足。
5. **开发成绩不等于泛化成绩。**已经依据 C14/C01 改过规则，就要把它们作为开发/回归题，不能再作为独立测试题宣传。
